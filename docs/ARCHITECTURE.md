# Architecture

## CURRENT — repository structure

The backend is one ASP.NET Core `.NET 10` project located under `src/GrindingThunder.Api` with `Controllers`, `Application`, `Domain`, and `Infrastructure` folders, accompanied by two separate HTTP-only frontends: the Razor Pages administrative back office and the Next.js player application described below. The backend folders organize code but do **not** create strict Clean Architecture or compile-time dependency boundaries.

- Controllers provide publication-filtered nation and exact-version vehicle-tree read endpoints plus a research calculation endpoint. Anonymous `GET /api/nations` projects only Published snapshots; the explicit authenticated `includeDrafts=true` path preserves the complete back-office catalog. `GET /api/vehicles/tree` requires a `ResearchTreeVersionId` and returns 404 unless that exact version is Published and belongs to the requested nation/category. The read controllers query EF Core directly and project response shapes; the research controller validates required IDs, positive RP/net-SL averages, and defined `ResearchOptimizationMode` enum values, delegates to `ResearchCalculatorService`, and maps calculation input failures to 400 or 404 responses.
- `Application` contains calculation request/result records, account DTOs, and calculation-specific exceptions. `Domain` contains the domain entities, `ResearchOptimizationMode` (located under `Domain/Entities/` so it is shared cleanly between calculations and persistent player preferences without cross-layer friction), and `IResearchCalculatorService`. `Infrastructure` contains the EF Core context, configurations, migrations, development seed, security services, and calculator implementation. PostgreSQL is configured through Npgsql.
- In Development, startup applies migrations and seeds sample data. The `GrindingThunder.Api.Tests` project (located under `tests/GrindingThunder.Api.Tests`) contains unit and integration tests for the calculator, version lifecycle, tabular import, authentication, and persistence models, using an in-memory SQLite database.
- One dependency direction is inconsistent with the intended boundary: `Domain.Services.IResearchCalculatorService` returns and accepts `Application.Models` records. Domain therefore depends on Application. The current implementation also uses EF entities inside the calculator.
- The versioned tree model keeps stable vehicle identity separate from snapshot state: `VehicleTreeEntry` stores version-specific RP/SL costs, rank, integer layout coordinates, and same-version folder membership; `TreeRank` stores version-specific rank configuration; and `VehiclePrerequisite` stores explicit version-scoped progression edges. Controllers project compatible flat vehicle fields only when exactly one entry exists and otherwise avoid choosing an arbitrary version.
- Stable identity is owned by one `ResearchTree`: Nation -> ResearchTree/category -> Vehicle. A required tree relationship and two composite entry foreign keys enforce ownership in PostgreSQL, while draft APIs and version validation provide useful application errors. The extra tree ID on entries carries this invariant between the two foreign keys; it contains no progression state. Import preview and commit resolve names only within the selected version's tree, and auto-created vehicles belong there. Tree-scoped generated-name uniqueness protects both API and direct database writes. Player progress continues using stable `VehicleId`.
- Research calculation requests explicitly identify a `ResearchTreeVersionId` and an optional `ResearchOptimizationMode` (defaulting to `LeastRp`). `ResearchCalculatorService` loads that version's entries, ranks, and prerequisite edges as one read-only split aggregate query, validates target/owned/filler membership, and traverses the graph in memory. After tracing the mandatory line and explicit fillers, it evaluates rank gates sequentially and auto-selects eligible researchable candidates to resolve rank shortfalls using the requested optimization mode (`LeastRp`, `LeastSl`, `FewestVehicles`, or `FewestMatches`) with deterministic tie-breaking ending on vehicle name. Auto-selected candidates pull their unresearched prerequisite chains and are flagged as rank-gate fillers. It totals version-owned RP and vehicle-purchase SL costs from the same deduplicated remaining-entry set, calculates separate ceiling-based match estimates, and returns their maximum as the combined estimate. It does not infer a version from a vehicle or query during recursion. Application-specific exceptions distinguish a missing version from invalid selected-version membership without leaking EF or dictionary exceptions through the API.
- Database-backed administrative authentication and authorization: JWT Bearer authentication is configured in ASP.NET Core middleware (`UseAuthentication()` and `UseAuthorization()`) using HMAC-SHA256 tokens. Three administrative roles (`Editor`, `Publisher`, `Admin`) and three authorization policies (`RequireEditorRole`, `RequirePublisherRole`, `RequireAdminRole`) protect administrative workflows. Role policies implement least-privilege access with Admin possessing supervisory access across all policies. Credential storage uses PBKDF2 with HMAC-SHA256 (16-byte salt, 100,000 iterations, constant-time verification) persisted in `AdminAccounts` and `AdminAccountRoles`. A safe, idempotent bootstrap (`AdminAccountBootstrap`) creates the initial Admin from configuration (`AdminBootstrap:Username` / `AdminBootstrap:Password`) on first run without overwriting existing accounts or restoring privileges on restart. Runtime token invalidation is enforced via an incremental `SecurityStamp` claim checked on authenticated requests, immediately invalidating active tokens upon password changes, deactivation, or role modification. `AdminAccountsController` provides protected account lifecycle endpoints (`/api/admin/accounts`), while `AuthController` provides login and identity inspection.
- Player identity and progression architecture:
  - Separate player audience and policy: player authentication uses `PlayerAccount` entities with PBKDF2 password hashes and normalized username/email uniqueness. JWT tokens are issued with a distinct audience (`PlayerAudience = "GrindingThunder.Player"`), enforced by `AuthPolicies.PlayerPolicy` (`RequirePlayerPolicy`). This prevents token confusion or privilege escalation between administrative and player accounts.
  - Dedicated player REST endpoints: `PlayerAuthController` exposes registration (`POST /api/player/auth/register`), login (`POST /api/player/auth/login`), and profile inspection (`GET /api/player/auth/me`). `PlayerProgressController` exposes progress retrieval (`GET /api/player/progress`) and atomic full-set replacement (`PUT /api/player/progress`).
  - Progress persistence and concurrency (`IPlayerProgressService` / `PlayerProgressService`): manages player-unlocked vehicles (`PlayerUnlockedVehicles`) linked to stable `VehicleId` and calculator preferences (`OptimizationMode`, `AverageRpPerMatch`, `AverageNetSlPerMatch`). Mutations use full-set replacement inside a database transaction guarded by an optimistic concurrency stamp (`ProgressStamp`), ensuring multi-device synchronization integrity.
  - Calculator decoupling: the research calculator (`POST /api/research/calculate`) remains completely anonymous and decoupled from persistence. Saved player inventories are not automatically injected; callers explicitly supply `unlockedVehicleIds` (intersected with the selected version's vehicle entries).
- Administrative CRUD and draft workflow architecture: dedicated controllers (`AdminNationsController`, `AdminVehicleTypesController`, `AdminVehiclesController`, `AdminGameUpdatesController`, `AdminResearchTreesController`, `AdminResearchTreeVersionsController`, and `AdminDraftsController`) expose secured endpoints for catalog entity management, version cloning/publishing/deletion via `IVersionLifecycleService`, and granular draft editing (ranks, entries, costs, coordinates, folder parents, and prerequisites). Endpoints enforce role-based authorization, guard against modifying published versions with HTTP 409 Conflict via `EnsureDraftVersionAsync`, and maintain composite foreign key single-version integrity.
- Tabular data import architecture (`ITechTreeImportService`, `TechTreeImportService`, and `TabularDataParser`): delivers a secure, two-phase import workflow under `/api/admin/drafts/{versionId}/import` (requiring `RequireEditorRole` and consuming `multipart/form-data`). `TabularDataParser` provides a zero-dependency parser using pure .NET BCL streaming APIs for RFC 4180 CSV/TSV and OpenXML XLSX archives. `TechTreeImportService` implements Phase 1 preview validation (evaluating format, data types, stable vehicle catalog matching, rank definitions, coordinate collisions, folder nesting constraints, prerequisite consistency, DAG acyclicity, and rank gate quotas without mutating database state) and Phase 2 commit (enforcing draft status and atomically upserting ranks, vehicles, entries, folder links, and prerequisite edges in a database transaction).
- Administrative back-office architecture (`GrindingThunder.Admin`): separate ASP.NET Core 10 Razor Pages web application under `src/GrindingThunder.Admin` serving on `http://localhost:5035`. It does not reference `ApplicationDbContext`, EF Core, or PostgreSQL directly. It communicates with `GrindingThunder.Api` exclusively via HTTP using a typed `ApiClient`. Web user sessions are managed using standard ASP.NET Core cookie authentication (`GrindingThunder.Admin.Session`), issuing auth tickets upon successful authentication against `POST /api/auth/login`. Outgoing requests to secured API endpoints automatically attach the stored JWT Bearer token using an `HttpContext`-aware `BearerTokenHandler` delegating handler. The application uses Tabler's Bootstrap 5-based UI through pinned CDN assets and provides authenticated catalog management pages for nations, vehicle types, vehicles, game updates, and research trees. Catalog mutations mirror existing API status semantics, and catalog delete controls and confirmation pages are restricted to Admin users.
- Dedicated player frontend architecture (`GrindingThunder.Web`): standalone Next.js App Router application using React 19, TypeScript, and Tailwind CSS, with no project reference to the API or Admin and no database access. It calls `GrindingThunder.Api` directly over HTTP through a small native-fetch client whose base URL comes from `NEXT_PUBLIC_API_URL` and defaults to `http://localhost:5034`. TypeScript DTOs mirror the publication-filtered nation catalog, exact-version vehicle tree, dedicated player auth/progress, and anonymous calculator contracts. A client-side session provider stores only the player JWT under a player-specific browser key, validates it through `/api/player/auth/me`, and never calls `/api/auth` or any `/api/admin` route. `/tree` cascades nation, category, and exact Published-version selection (defaulting to the API-ordered latest version), defensively excludes non-Published catalog data, and projects that snapshot into a deterministic React/SVG canvas. Its presentation-only layout uses each version-owned rank plus persisted `TreeColumn`/`TreeRow`, same-cell folder stacking, and only the response's explicit prerequisite/folder IDs; it does not reproduce backend traversal or validation. The canvas supplies acquisition-styled vehicle cards, rank quotas, distinct relationship connectors, pan/zoom/fit/reset controls, and a responsive selection drawer with prerequisite, folder, and Wiki details. Ownership, calculator execution, and progression overlays remain deferred. The landing, login, registration, and profile routes share the responsive dark-themed shell.
- Public tree architecture: `/Tree` is explicitly anonymous in Razor Pages conventions and calls only the publication-filtered catalog and exact Published-snapshot endpoint. Nation, ResearchTree, and version IDs are revalidated against the returned hierarchy before entries are requested. It maps through `VisualTreeMapper.FromPublic` and renders the same `_VisualTree.cshtml`, `visual-tree.js`, CSS, and SVG routing used by the admin workspace. Read-only card selection opens a presentation-only details panel; no public Page handler or mutation form exists.
- Version editor: server-rendered Razor forms and tables under `/Trees` browse versions, create/clone drafts, delete drafts, and manage ranks/quotas, entries/costs/acquisition types, numeric layout coordinates, folder parents, and prerequisite edges through existing REST endpoints. The shared visual workspace introduced in Batch 25 renders one exact version as version-defined rank bands, acquisition-styled vehicle cards, solid prerequisite connectors, and distinct dashed folder connectors. Draft editors can select, drag/nudge, inspect, add, and remove entries; use the mutually exclusive prerequisite editor; and use Batch 32 layout assistance for bounded same-rank multi-selection, alignment, distribution, and group movement. Layout assistance keeps `TreeColumn` / `TreeRow` as non-negative integer coordinates, previews occupied and potential cells, highlights folder relationships and root-cell collisions, and saves through the existing per-entry coordinate endpoint after server-side membership and final-layout validation. Drag snapping and layout guides are client presentation state only. Canvas coordinates never infer or mutate prerequisite data. Editor/Admin users can edit drafts; Admin alone can delete one. Published versions omit all visual mutation controls and load through the same exact Published-snapshot endpoint used by `/Tree`. All roles can validate and compare versions through public endpoints. Publisher/Admin users can publish drafts through the secured publish endpoint after an explicit immutable-snapshot confirmation; the backend repeats validation and rejects invalid drafts. The Editor/Admin `/Import` page previews multipart CSV/TSV/XLSX uploads and retains valid file bytes in a 15-minute in-memory cache keyed to the user and version for a confirmed commit. The public comparison screen only sends version IDs confirmed to belong to the same tree. The test mock API handler enforces backend Editor, Publisher, and Admin role policies on `/api/admin/` routes. Hermetic admin integration tests use single-role sessions and recorded HTTP requests.
- Account-management UI: Razor Pages under `/Accounts` (`Index`, `Create`, `Edit`) restricted to Admin users via `[Authorize(Roles = "Admin")]`. Admins can inspect the account list, provision new accounts with selected roles, edit username and active status, and replace account passwords, with immediate Bearer token propagation and API conflict feedback (such as last-Admin preservation or duplicate username rejection).
- Game Update release workspace: `/Catalog/Game-Updates/{id}/Workspace` composes the existing HTTP lifecycle endpoints without introducing a release service or database model. `GET /api/nations` includes `GameUpdateId` on each version projection so the Admin client matches the selected update by stable identity rather than display text; its split query avoids a multi-collection query warning. Publisher can read one secured Game Update's metadata, while list/create/update/delete permissions retain their existing boundaries. For each tree, the page chooses only that tree's latest Published snapshot as its clone/diff baseline, validates Drafts through the existing public endpoint, and delegates publication to the existing backend validation and immutable transition. Server-side POST guards reconstruct the workspace and reject mismatched tree, update, version, or clone-source IDs before issuing lifecycle calls.

## Batch 23 vehicle API contract

- `POST /api/admin/vehicles` now requires `{ researchTreeId, name, imageUrl? }`. Omitted/empty or unknown ownership returns 400; a normalized duplicate within the tree returns 409. This intentionally replaces creation of globally unowned vehicles. `PUT` continues accepting name/image only, preserving stable ownership.
- Admin vehicle DTOs and public vehicle projections add `researchTreeId`, `nationId`, `nationName`, `vehicleTypeId`, and `vehicleTypeName`. Existing public IDs and version-specific/flat fields keep their meanings; entities are never serialized directly.
- Adding a vehicle entry from another tree returns 400 before saving. PostgreSQL independently rejects invalid entries through composite foreign keys.
- Batch 23 initially provided matching DTOs, a tree selector on vehicle creation, ownership labels, and a tree-filtered draft vehicle picker. Batch 24 replaces the vehicle ownership selector with the contextual workflow below.

## Batch 24 contextual back office

- `/Trees` lists nations, `/Trees/{nationId}` lists enabled ResearchTree categories and offers missing VehicleTypes to Editor/Admin users, and `/Trees/{nationId}/{researchTreeId}` lists that tree's versions. The existing version detail, import, validation, comparison, and publication workflows keep their semantics. Old `researchTreeId` query bookmarks remain readable.
- Vehicle pages use `/Trees/{nationId}/{researchTreeId}/Vehicles` and nested Create/Edit/Delete routes. Shared `TreeContextPageModel` checks the nation/tree pair through `IApiClient`; edit/delete additionally verify the vehicle's owner before sending a mutation. Route-bound IDs prevent posted form values from replacing ownership. Name/image input contains no ownership property, and updates still send only name/image.
- `GET /api/admin/vehicles/tree/{researchTreeId}` is the only new API endpoint. It returns stable vehicle DTOs filtered in the database, including identities without version entries, and permits Admin, Editor, and Publisher roles. Unknown trees return 404; empty trees return an empty list. Existing global catalog endpoints and mutation policies retain their authorization. Reusing the public vehicle-tree projection would omit identities with no version entries, while the global vehicle projection also loads unrelated snapshot data.
- Administration groups existing nation/category screens and Admin-only accounts; Game Updates remains separate. The Dashboard changes only module navigation. Shared breadcrumbs and Vehicles/Versions links retain context, including return navigation from version detail and comparison screens. No database, domain, dependency, or project-boundary changes are needed; the Admin client remains HTTP-only.

## TARGET — direction

Remain a modular monolith and keep the backend in one project for now, with the separate HTTP-only admin client. Keep controllers focused on HTTP validation and response handling; keep progression and costing rules separate from controllers and presentation. Use EF Core directly where it is appropriate, with DTOs or projections at API boundaries instead of exposing EF entity graphs. Avoid generic repository and UnitOfWork wrappers, MediatR, CQRS, AutoMapper, microservices, and similar abstractions unless a concrete requirement later justifies them.

The service contract's location and request/result types should be reconciled when the calculation boundary is changed; a folder name alone cannot enforce dependency direction. Separate Domain, Application, Infrastructure, and API .NET projects are not currently required. Reconsider that split if compile-time dependency enforcement becomes valuable enough to justify the added project and reference management.
